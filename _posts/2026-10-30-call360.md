## A rep has seconds

The phone rings. On the other end is Jane Doe, a member in her late 60s.

In the last few weeks, Jane had a routine office visit. Her pharmacy rejected a prescription because the drug wasn't on the preferred list. A prior authorization was approved after five days. She has an open billing grievance, and she already called once about a delayed refill.

That history exists, but it's spread across claims, pharmacy, authorization, grievance, and call systems. The rep has a few seconds to understand it before saying hello.

**Call360** is the service we built to solve this. It turns a member's recent healthcare activity and past calls into short, personalized talking points. The talking points appear in the agent desktop and case-prep tools reps already use, through a real-time API.

## Architecture overview

Call360 reads from source data for calls, claims, prior authorizations, grievances, surveys, and real-time member events. It has three layers:

1. **Warehouse and pipelines** run on Cloud Composer. Daily batch jobs land source data in BigQuery, where PII is tokenized, staging tables are built, and call transcripts are summarized. Real-time member events are ingested hourly.
2. **Serving layer** keeps one Bigtable table per domain, such as calls, claims, Rx, prior auth, and grievances. Each row is keyed by `memberId#eventDate` and expires after 90 days.
3. **Call360 API** runs on GKE and calls Gemini 2.5 Flash-Lite on Vertex AI in two passes, summarizing and then formatting JSON. It returns talking points to the rep's agent desktop.

## The two-layer data pattern

The core idea is simple: **store the data in the shape it's read in.**

| Layer | Store | Holds | Used for |
|---|---|---|---|
| 1 | BigQuery | Analytics-ready tables, full history | Reporting and analysis |
| 2 | Bigtable | Key-value data, 90-day window (TTL), up to 2 versions per column | Real-time API lookups |

Every source is keyed by the **same member ID**: call summaries from several lines of business, plus medical claims, Rx claims, prior authorizations, grievances, and surveys. Together they form one member-centric view, refreshed daily.

BigQuery is the system of record for history. Bigtable is a narrow, fast window of what's relevant right now. The TTL keeps the serving layer lean on its own, so we don't need cleanup jobs.

## The reusable pipeline framework

Call360 pulls from **9 sources**, each with its own format. Instead of building 9 pipelines, we built one framework that every source runs through.

<figure class="diagram">
{% include diagrams/c360-framework.svg %}
<figcaption>Figure 3: Every source follows the same four BigQuery steps, then one factory DAG loads it into Bigtable.</figcaption>
</figure>

**Step 1: BigQuery.** Every source follows the same four steps: pick the eligible members, join their events, turn codes into readable text, and write to production. Only the SQL changes from source to source.

**Step 2: Bigtable.** One factory DAG reads a YAML list of sources and creates a load job for each one. Adding a source means adding a config entry, not writing a new pipeline:

```yaml
# registry entry (mock)
source: { table: member_call_summary }
target: { table: calls }
row_key: [member_id, event_date]
```

### Readable data for the LLM

This is where the two teams' work meets. We never hand the LLM raw codes:

```
Before:  status_cd = D,  svc_desc = RX NON-PREF
After:   denied_rx_claims = "Non-preferred drug – denied"
```

Readable input means shorter prompts and fewer misreads. The pipelines also map every source's member ID to **one global ID**, so Jane's pharmacy history and her call history belong to the same person.

### Safe to rerun

The framework handles the usual failures once, for every source:

| Problem | How it's handled |
|---|---|
| A run fails halfway | Production is written only after an audit check passes |
| Two runs overlap | Each run has its own ID, and duplicates are blocked |
| A day is missed | The next run starts from the last *successful* one |
| A dev run hits prod | Dev runs always write to separate `_temp` tables |

## The row key is the design

Bigtable has one index, the row key, so the row key *is* the design.

- **`memberId#eventDate`**. The high-cardinality member ID comes first, which spreads writes evenly and avoids hotspots. The date comes second, which allows prefix scans for a whole member or range scans by date.
- **One table per domain**, such as calls, claims, Rx and prior auth. Every table uses the same key, so one member ID finds Jane's rows in all of them. Adding a source means adding a table and a registry entry, with no change to the others.

*Sample row-key builder (mock data):*

```python
def build_row_key(member_id: str, event_date: str) -> str:
    # High-cardinality member ID first to avoid hotspotting;
    # date second enables per-member prefix and range scans.
    if not member_id or not event_date:
        raise ValueError("Null keys are dropped before load")
    return f"{member_id}#{event_date}"

build_row_key("MBR-000123", "2025-01-15")  # -> "MBR-000123#2025-01-15"
```

## Choosing Bigtable: the benchmarks

Before committing, we benchmarked the realistic options on **5 million records**.

| Read pattern | Bigtable | Spanner |
|---|---|---|
| By member ID | ~26.6 ms | ~620–660 ms |
| By member ID + call date | ~27.1 ms | ~620–660 ms |
| By member ID + LOB | ~28.9 ms | ~620–660 ms |
| Batch write (per record) | ~0.57 ms | ~0.17 ms |

That's about **23× faster reads**. Spanner was faster for batch writes, but Call360 is a **read-heavy** API, and writes happen in daily batches, so reads won.

We also ruled out two other options:

- **BigQuery for serving.** Each request would need data from 8+ warehouses, aggregated in memory, which adds latency on every call.
- **A relational database.** It adds overhead we don't need for what is basically a lookup by member ID.

**The trade-offs:**

- **One index.** Any access pattern that doesn't start with the member ID is expensive.
- **Object size.** Member objects can grow large.
- **Multi-region disaster recovery takes extra design.** Options we considered were dual writes, change streams with Dataflow, and periodic dump and load.

## Walkthrough: one member, end to end

Here is Jane Doe's path through the system, in the same order as Figure 2. Everything below is mock data.

### 1. Overnight: the pipelines load her data

The daily DAGs write each source to BigQuery as readable, PII-tokenized rows, then load them into the matching Bigtable table. After the run, Jane's recent history looks like this:

```
table        row key                  value
calls        MBR-000123#2025-01-14    reason: "Refill delay"
                                      outcome: "Check with pharmacy"
claims       MBR-000123#2025-01-08    "Routine office visit – paid"
rx           MBR-000123#2025-01-12    "Non-preferred drug – denied"
prior_auth   MBR-000123#2025-01-10    "Approved after 5 days"
grievances   MBR-000123#2025-01-13    "Billing question – open"
```

### 2. Jane calls: the request comes in

The agent desktop asks Call360 for member `MBR-000123`. The gateway checks the OAuth token, and the request is written to the audit trail.

### 3. The API reads her rows

The API runs the same prefix scan, `MBR-000123#`, on each domain table and gets back everything from the last 90 days. Each read takes about 27 ms.

### 4. Few-shot selection

Data science keeps a small library of example summaries. A Sentence-BERT model picks the one closest to Jane's situation, so Gemini sees a good example of what to write.

### 5. Pass 1: summarize

Gemini 2.5 Flash-Lite gets Jane's context and the chosen example, and writes a short summary. The prompt forbids guessing beyond the context.

```
SYSTEM:
You are an assistant that helps customer service representatives prepare
for calls. Using only the member context provided, write a brief summary of
the member's recent activity and likely reasons for calling. Do not guess.
Do not include information that isn't in the context.

EXAMPLE (few-shot):
Context: Paid claim for lab work; one prior call about an ID card.
Summary: Member recently had lab work that was paid. They called before
about an ID card, so they may be following up on that.

MEMBER CONTEXT:
- Paid medical claim: routine office visit
- Denied Rx claim: non-preferred drug
- Prior authorization: approved after 5 days
- Open grievance: billing question
- Prior call: refill delay
```

### 6. Pass 2: format JSON

A second call to the same model turns that summary into strict JSON, so the agent desktop can render it without any parsing surprises.

```
Convert the summary below into JSON with exactly this schema:
{"member_id": string, "talking_points": [string]}
Rules:
- 3 to 5 talking points, each under 25 words.
- No text outside the JSON.
- Do not add facts that are not in the summary.
```

### 7. Talking points on the agent desktop

```json
{
  "member_id": "MBR-000123",
  "talking_points": [
    "Member may be calling about a recently denied prescription for a non-preferred drug.",
    "Previous call was about a refill delay; confirm whether it has been resolved.",
    "Prior authorization was approved after 5 days; member may want confirmation.",
    "There is an open billing grievance; check its status before the call."
  ]
}
```

That JSON is exactly what fills the panel at the top of this post.

## Lessons learned

1. **Design storage around the read pattern.** One well-chosen row key beat a more flexible database by more than 20× on reads.
2. **Make data LLM-ready upstream.** Human-readable status buckets and drug names simplify the prompts and reduce misinterpretation.
3. **Config beats code.** One factory DAG and a YAML registry handled 9 datasources.
4. **Operational safety is a feature.** Audit states, run isolation, watermarks, and `_temp` dev tables prevented whole classes of incidents.
5. **Treat the hand-off between teams as a design.** Readable, member-keyed context is the contract between data engineering and data science. The clearer it is, the more each team can change its own side without breaking the other.
6. **Be honest about trade-offs.** A single index, growing objects, and DR are real costs of Bigtable.
